# 优化点 22：HEVC CABAC 旁路位批量读取

## 代码走读

系数幅值、符号等语法元素包含连续的 CABAC bypass 位。旧实现对每一位
调用一次 `get_cabac_bypass`，重复进行范围比较和状态更新。
`cabac_bypass_bits` 把连续位的解码视为同一归一化区间中的商：
输入偏移左移 `n` 位，除以编码区间 `range << (CABAC_BITS + 1)` 得到
`n` 位结果，余数更新解码状态。若输入跨过补充字节边界，先补入字节；
若无法安全走批量路径，则回退到原来的逐位读取。

`cabac_unary_prefix` 同理批量查找一串前导 1，遇到第一个 0 时调整
解码状态和消费位数。系数绝对值余数和长度大于 2 的符号位使用这些函数；
短序列仍使用旧路径。此改动适用于相同语法规则的输入，不依赖视频内容
特征，也不改变线程数。

## 验证

2026-09-26 从优化点 21 和 22 对应的 Git 提交重新导出干净源码，
使用相同鲲鹏 920、GCC 静态配置和输入。两版都固定 16 个解码线程，
避免早期自动线程补丁影响代码收益对照。完整命令：

```bash
ffmpeg -nostdin -v fatal -threads 16 \
    -i /data/wanglimin/HEVC-720p-10min.mov \
    -frames:v 15000 -an -sn -vf format=rgb24 -f null -
```

| 交叉顺序 | 优化点 21 后 `real` | 再加本优化 `real` |
|---|---:|---:|
| 对照 → 本优化 | 30.011 s | 30.460 s |
| 本优化 → 对照 | 30.006 s | 29.470 s |

单独叠加的均值仅下降 0.044 秒（约 0.14%），小于本次波动，
**不能宣称本补丁单独有稳定收益**。原报告的 0.372 秒数字来自混有
未提交试验代码的构建，已由以上干净构建结果取代。

另一个同线程数交叉测试直接比较“21 + 23”和“21 + 22 + 23”：
前者为 29.588/29.603 秒，后者为 28.866/28.623 秒，平均差约
0.851 秒。这个结果支持保留 22 作为组合的一部分，但不能证明其
单独收益，也不能据此断言具体的机器级因果机制。

3000 帧 RGB24 `framemd5` 管道 SHA-256 与对照一致：
`9bf7a192699267ddfb6615887231209758dcdc695aa740c6ca75cb5f4709f792`。
不把该收益直接外推到其他输入；20 秒目标尚未达到。
